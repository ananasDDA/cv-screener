Local-first

Runs on your machine

Claude starts the server as a subprocess and talks to it over stdin and stdout. Nothing listens on a port and nothing is uploaded.

A stdio MCP server

cv mcp speaks the Model Context Protocol over stdio. Your Claude client is the agent, so no LLM API key is needed for MCP.

Local embeddings

CV text is embedded with bge-small through fastembed (ONNX, on the CPU). The index is a local ChromaDB store, built on first run — under ~/.cv-screener when installed as a package, or in data/ in a git checkout.

A private library

Résumés you add through Claude are real people's data, so they are written to ~/.cv-screener/candidates — outside the repository, never committed.

Install

Add it to Claude

Requires uv; Python 3.12 is fetched by uv automatically. The first start takes 30–60 seconds while dependencies install, a ~130 MB embedding model is downloaded once and the index is built.

Claude Code

One command in your terminal.

claude mcp add cv-screener -- uvx --from git+https://github.com/ananasDDA/cv-screener cv mcp

Claude Desktop

Merge into claude_desktop_config.json (Settings → Developer → Edit Config). macOS: ~/Library/Application Support/Claude/claude_desktop_config.json · Windows: %APPDATA%\Claude\claude_desktop_config.json

{
  "mcpServers": {
    "cv-screener": {
      "command": "uvx",
      "args": ["--from", "git+https://github.com/ananasDDA/cv-screener", "cv", "mcp"]
    }
  }
}

Enable the tools in the chat. Claude Desktop keeps tools from a new local server switched off until you turn them on in the chat's tools menu, and it asks again whenever a tool's definition changes. Quit and reopen the app after editing the config.

If Claude Desktop cannot find uvx, use its absolute path — for example /opt/homebrew/bin/uvx on macOS. Find it with which uvx.

Verify with claude mcp list: cv-screener should report Connected. Then ask Claude “Which candidates speak Spanish?” or “Show me the whole collection”.

For AI agents: a machine-readable runbook lives at install.md, indexed from llms.txt.

How it works

From a persona grid to three search functions

01

A designed persona grid

14 hand-written persona specs fix role family, seniority, country, stack and languages, so the diversity of the dataset is designed rather than hoped for. Seeded Faker supplies names and contacts per country locale.

02

Profiles written by an LLM, validated by Pydantic

The model writes only the narrative, as JSON matching the Candidate schema; schema errors are retried. One JSON file per candidate, rendered to a PDF résumé in one of three layouts.

03

ChromaDB with metadata flags

One document per candidate: the CV text embedded with bge-small plus scalar metadata and a boolean flag per language and per skill variant, so exact filters and semantic ranking work on the same store.

04

One search boundary

search(query, filters, k), get and find_by_name cover filter-only, semantic and hybrid retrieval. The CLI agent and this MCP server both use exactly those three functions — the index knows nothing about the LLM.

Field test

Tried on 2,483 real résumés

The project is built on 14 synthetic CVs, so I took its embedder to the public Kaggle Resume Dataset. No fine-tuning and no LLM calls. It reaches 71% category accuracy where the popular notebooks report 53 to 68%. A typed role brings back 73% right résumés in the top ten, and 90% once a plain word match joins the ranking.
